# 开发历程：MoonSign

这份文档记录 MoonSign 是怎么一步步长出来的：为什么这样分层，哪里翻过车，哪些决定事后看仍然成立。功能说明在 README 和 `docs/USAGE.md`，这里只讲过程。

- 周期：2026-11-04 → 2026-11-22
- 规模：54 个 `.mbt` 文件、10,176 行（其中源码 8,136 行、测试 2,040 行）、21 个包
- 提交：86 次；测试：73 个；发布：24 个版本（最新 `0.23.1`）
- 依赖：`pdflite`（PDF 解析/写入）、`mooncry`（密码学原语）、`moonbitlang/x`、`moonbitlang/async`

## 一、起点

选 PDF 签名，是因为 MoonBit 生态里已经有 PDF 库和密码学库，但中间"把签名写进 PDF、再验回来"的那一层是空的。这一层不难在算法，难在字节：DER 的集合排序、CMS 的签名属性、PDF 的 `/ByteRange` 和 `/Contents` 占位，任何一处差一个字节，OpenSSL 或 Adobe 就不认。

所以第一天的目标定得很小：**能签、能被 OpenSSL 验**。PAdES B-B 先跑通，时间戳、证书链、国密都往后放。

## 二、时间线

**11 月 4 日：从零到一条能跑的链路。**
脚手架、DER 编解码、X.509 最小解析、CMS SignedData、PDF 签名域、CLI，一天内全部落地，并用 OpenSSL 做了第一轮互操作。当天就发现 ESS `signingCertificateV2` 的嵌套写错了——这类错误自己验自己永远发现不了，必须让外部工具验。

**11 月 10 日：把"能签"补成"能用于真实材料"。**
加了 PKCS#12（.p12/.pfx）、OCSP、证书链、CRL，以及 `cmd/bench` 和 `docs/PERFORMANCE.md`。这一天版本号从 0.2 走到 0.10，看起来快，其实大量时间花在 PKCS#12 的 MAC 和 AES 上（见踩坑）。

**11 月 12 日：签名的"人"和"第二次签名"。**
可见签名、自动显示证书 CN、给已签名 PDF 追加第二个签名、一次验证多个签名。追加签名是这一阶段的硬骨头：旧字节不能动，否则旧签名会失效。

**11 月 15–16 日：国密、加密、长期验证材料。**
SM2/SM3、加密 PDF、DSS/VRI、填写已有空白签名域。国密的坑不在算法，在 OpenSSL 的默认用户 ID 和我们的标准 ID 不一致。

**11 月 17–22 日：收口。**
可见签名页码、首次签名改增量、去掉重复解析、多页带文字/链接的兼容样本、加密 + 二次签名组合测试，最后修了可见签名外观（日期被裁、链接显示成空框）。

## 三、几个关键取舍

**核心只吃字节、吐字节。**
库不读文件、不联网、不读系统时间。文件读写、网络、时钟都在 CLI 层。好处是测试完全确定，同一输入在任何平台结果一致；坏处是 CLI 必须自己处理时间、路径和错误提示。事后看这个边界是对的：`pades` 的测试不依赖环境，CI 在四个平台跑同一套断言。

**VALID 不等于 TRUSTED。**
`verify --cert` 只回答"签名和这张证书是否匹配、文件有没有被改"；`--anchors` 才回答"这张证书能不能链到你信任的根"。这两个问题混在一起，用户就会把"签名有效"当成"文件可信"。CLI 的输出和退出码（0/2/3）都按这个区分设计。

**第一次签名也尽量增量。**
最初怕增量写入把 PDF 写坏，第一次签名用整篇重写，只有追加才增量。后来发现重写会改变原文件的排版细节，而且大文件更慢；于是改成"先试增量，失败再回退整篇重写"。加密 PDF 例外：先解密，再重写。

**DSS 只存材料，不替用户做信任决定。**
`dss` 命令把证书、CRL、OCSP 和 VRI 写进 PDF；`verify` 会自动用这些材料补链、查吊销，但根证书仍然要用户用 `--anchors` 指定。我们不内置"可信根列表"，因为那等于替用户决定信任谁。

## 四、踩过的坑

**pdflite 的增量更新，读回来是旧对象。**
第一版用增量写入做首次签名，再用 pdflite 读回来，发现改过的对象还是旧值。复现后确认是库的读回问题，于是首次签名退回整篇重写，只对"追加"使用增量。到 0.23 又改成"增量优先 + 失败回退"，但这次不再依赖读回，而是直接相信写出的字节。

**PKCS#12 的 MAC 对不上。**
按 RFC 7292 实现 KDF 时漏了 `D=id×64` 的填充，MAC 一直错；AES 解密又把 IV 当成密文的一部分；密码的 BMP 编码用了 UTF-16LE，实际是 UTF-16BE。三个问题叠在一起，最后是拿 OpenSSL 生成的 p12 逐字节比对才定位。

**SM2 的默认用户 ID。**
用 OpenSSL 生成 SM2 签名做互操作，验签一直失败。原因是 OpenSSL 默认的 `distid` 和 GB/T 32918 的标准 ID 不一致。重新生成证书时显式带上 `distid:1234567812345678`，并把标准向量写进测试，才把这件事钉死。

**OCSP 的 issuerNameHash 用错了对象。**
最初拿 `issuer.der` 去算哈希，应该用 `issuer.subject_raw`（Name 的 DER，不是整张证书）。症状是 `CertMismatch`，看起来像响应不匹配，其实是哈希输入错了。

**测试证书会过期，CI 也会因此变红。**
OCSP 响应最初只给 7 天有效期，第 7 天 CI 突然失败，报"response outside its validity window"。后来把 OCSP 有效期改成 10 年，并把测试里的固定时间调进有效窗口。这件事提醒我：**带时间的测试数据必须比项目寿命长**。

**CI 的 YAML 少一个换行，任务 0 秒失败。**
用脚本往 workflow 里插步骤，插入点和上一条命令粘在一起，GitHub Actions 直接解析失败，日志里只有 "Process completed with exit code 1"。犯过两次，后来每次改 YAML 都先本地解析一遍。

**PowerShell 的编码把中文文档弄乱。**
用 `Get-Content -Raw` 读 UTF-8 中文再写回，没有指定 `-Encoding UTF8`，README 和 DESIGN 各乱过一次。恢复方式是从 git 取回上一版，再用编辑工具重新改。之后所有中文文件只用编辑工具或显式 UTF-8 读写。

**签名框的日期跑到页面外。**
可见签名的文字从框底往上排，第二行被裁到页面外；示例 PDF 的链接注释又默认画边框，看起来像两个空白签名框。这两个问题在测试里都"通过"，因为测试只检查结构，不渲染。最后用 PDF 渲染器看了第 2 页才发现，0.23.1 修复：文字从框顶排、日期改成可读格式、链接注释不画边框。

**新工具链把旧 API 标成废弃。**
CI 用最新 MoonBit，某天 `Int64::from_int` 变成 warning，lint 直接失败。本地工具链还是旧版，复现不了；升级到同一天的最新版后，一次抓出 12 处。这件事的教训不是"别用旧 API"，而是**本地和 CI 的工具链版本要一致**。

## 五、测试与互操作

测试分三层：

1. **单元测试**：DER、OID、时间、X.509、CMS、CRL、OCSP、PKCS#12、SM2、PDF 对象操作。
2. **端到端测试**：签名 → 验签、篡改 → 失败、二次签名 → 两个都有效、加密 PDF、DSS、空白签名域。
3. **外部互操作**：CI 把 MoonSign 生成的 CMS/PDF 交给 OpenSSL 和 pyHanko 验；也让 pyHanko 签一份 PDF，MoonSign 来验，并在它上面追加签名。

固定测试材料（证书、CRL、OCSP、p12）由 `scripts/gen_fixtures.py` 生成，生成结果提交进仓库，CI 不依赖网络和 OpenSSL 的版本差异。

有几类测试是"故意找茬"的：把 `/ByteRange` 改短、把 `/Contents` 改一个字节、把证书换成另一张、把 OCSP 响应换成过期的、用错误的 PDF 密码。这些负向测试比正向测试更能说明边界在哪里。

## 六、AI 在这个项目里的角色

代码主要由 AI 编码代理完成，我负责方向、范围、验收和取舍：先定"这一版只做 B-B"，再看互操作结果决定下一步；每次发布前跑 `moon fmt`、`moon check --deny-warn`、`moon test`，CI 绿了才发。

AI 写得快，但也确实犯过错，而且不是小错：

- 把中文文档的编码弄乱；
- 往 CI 里插步骤时漏换行；
- 文档里留着"不支持加密 PDF""不能追签"这类已经过时的说法；
- 可见签名只检查了结构，没检查渲染。

这些错误的共同点是：**自动化检查覆盖不到**。后来补的措施也很具体：文档改动后用 `git diff` 看一遍、CI 加完整示例、可见签名用渲染器看一眼。AI 能写代码，但"这件事到底对不对"仍然要靠可复现的检查。

## 七、如果重来

1. **第一天就把"外部工具验"写进 CI**，而不是等到功能做完。互操作是最早暴露问题的地方。
2. **测试材料的时间跨度按项目寿命设计**，不要用 7 天有效期的 OCSP。
3. **文档和代码在同一个提交里改**，避免"代码已支持、文档还写着不支持"。
4. **可见签名一开始就用渲染器验收**，不要只看 PDF 里有没有 `/AP`。

## 八、现在的位置

- 签名格式：PAdES B-B，可选 B-T；DSS/VRI 材料已支持；
- 算法：RSA PKCS#1 v1.5、ECDSA P-256、SM2/SM3；
- PDF：首次签名增量追加（失败回退）、二次签名、加密输入、空白签名域、可见签名与页码；
- 验证：证书链、CRL、OCSP、时间戳链、DSS 自动取材料、多签名逐个验证；
- 互操作：OpenSSL、pyHanko 双向验证；
- 已知差距：完整的 B-LT 验证策略、TSA 联网、复杂第三方 PDF 的更多样本、SM2 在主流阅读器里的显示支持。

这些差距都写在 README 和 `docs/COMPATIBILITY.md` 里，没有藏起来。
