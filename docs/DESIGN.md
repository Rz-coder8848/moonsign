# 设计说明

本文用大白话解释 MoonSign 是怎么工作的，以及为什么这样分层。

## 一句话

把 PDF 当成一串字节：先留出一块空白位置放签名，再把这串字节（除了那块空白）算一个指纹，用私钥把指纹签了，最后把签名填回空白处。验签就是反过来：按文件里记录的"覆盖范围"重新算指纹，再检查签名对不对。

## 分层

```
pades/   对外入口：sign_pdf / verify_pdf（把下面几层串起来）
  │
cms/     CMS SignedData：签名容器（谁签的、用的什么算法、签名值）
  │
pdf/     在 PDF 里加签名域、写 /ByteRange、填 /Contents
  │
der/     ASN.1 DER 编码（CMS 和证书的"字节语法"）
  │
crypto/  摘要与签名算法（调用 mooncry）
```

另外两个辅助包：

- `x509/`：读证书，拿到签发者、序列号、公钥、有效期；
- `pem/`：读 `openssl` 生成的 `-----BEGIN ...-----` 文件。

## 签名流程

1. 读 PDF，找到第一页；
2. 新建一个"签名框"（不可见），挂到页面上，并登记到 AcroForm；
3. 写一个签名占位：`/Contents` 里先放 16384 个 `0`，`/ByteRange` 先放四个固定宽度的数字；
4. 把占位改成 `<...>` 十六进制字符串，并按真实位置回填 `/ByteRange`；
5. 计算两段字节的 SHA-256（跳过 `<...>` 这一段）；
6. 组装 CMS：把摘要、签名时间、证书指纹放进去，用私钥签名；
7. 把 CMS 转成十六进制，填进 `<...>`，不够的地方补 `0`；
8. 输出新 PDF。

## 验签流程

1. 读 PDF，找到所有 `/FT /Sig` 的签名框；
2. 读 `/ByteRange`，检查它是否正好把"除签名值以外的所有字节"都覆盖了；
3. 按 `/ByteRange` 重新算摘要；
4. 解析 CMS，检查里面记录的摘要和刚算出来的是否一致；
5. 用证书公钥验证签名；
6. 输出 VALID / INVALID。

## 为什么核心只吃字节、吐字节

`cms/`、`pdf/`、`pades/` 都不直接读文件、不联网、不读系统时间。好处是：

- 测试可以完全确定（同样的输入永远同样的输出）；
- 同一套代码可以跑在 native、wasm、js 上；
- CLI 只是薄薄一层壳，换一个运行环境不用重写核心。

## 为什么自己写 DER

CMS 对字节非常挑剔：一个 tag 写错、SET 里的元素顺序不对，验证方就会拒绝。现成的 ASN.1 库版本还很低，把这种"必须一位不差"的工作外包出去风险更大，所以 `der/` 自己实现，只依赖标准库。

## 整篇重写 vs 增量追加

标准做法是在原文件后面"追加"一版（增量更新），这样旧签名仍然有效。

- **第一次签名**：仍采用"整篇重写后再签名"。`pdflite` 自己写出的增量更新再用它自己读回来时，改过的对象会解析成旧版本（已复现），所以首次签名不依赖它。
- **追加签名**：从 0.13 起，用 `pdf_write_document_incremental_update_with_xref_stream` 只追加新对象（新签名域、更新后的 Annots/AcroForm、新的 xref），旧字节一个不动，因此旧签名保持有效。CI 会签名两次并分别验签。

限制：追加功能目前在我们自己生成的 PDF 上验证过；对 Adobe/pyHanko 生成的复杂 PDF，兼容性还需要更多测试。

## 错误模型

每一层都有自己的错误类型，最外层 `PadesError` 负责把它们串起来，并给出人能看懂的一句话。CLI 会打印这句话，并以退出码区分：

- 0：成功 / 验签通过
- 2：验签不通过（文件被改过，或证书不对）
- 1：用法错误、文件读写失败、格式不支持
